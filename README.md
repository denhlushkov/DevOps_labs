# Лабораторна робота №2: Контейнеризація застосунків

**Варіант:** Task Tracker (БД PostgreSQL, Порт 3000).

Цей репозиторій містить практичну реалізацію контейнеризації веб-застосунку за допомогою Docker Compose, а також звіт із дослідження різних підходів до створення Docker-образів (кешування шарів, базові образи, багатоетапна збірка).

---

## 🚀 Практична частина: Запуск Task Tracker

Система складається з трьох сервісів, які розгортаються в ізольованій Docker-мережі `devops-net`:
1. **web:** Node.js застосунок. Образ збирається локально на базі `node:20-alpine` з оптимізацією шарів.
2. **db:** PostgreSQL 15. Дані зберігаються персистентно у volume `pgdata`.
3. **nginx:** Reverse-proxy сервер, який прокидає порт 80 на хост.

### Інструкція з розгортання та тестування

1. Клонуйте репозиторій та перейдіть у директорію проєкту:
   ```bash
   git clone <url_репозиторію>
   cd devops_labs
2. Запустіть інфраструктуру в фоновому режимі:
   ```bash
   docker compose up -d --build
3. Тестування (ендпоінти доступні на localhost:80)::
   ```bash
   # Отримання HTML-сторінки (поверне список доступних роутів):
    curl.exe -H "Accept: text/html" http://localhost/

   # Отримання списку задач у форматі JSON:
    curl.exe -H "Accept: application/json" http://localhost/tasks

## 🔬 Дослідницька частина

Нижче наведено результати експериментів з оптимізації Docker-образів. Вимірювання часу збірки проводилися у Windows PowerShell за допомогою командлета `Measure-Command`.

### 1. Python Application (Оптимізація шарів та залежностей)

**Мета:** Дослідити вплив кешування шарів (`layers`) на час збірки образу та різницю компіляції важких C-залежностей (`numpy`) на різних базових ОС (Debian vs Alpine).
**Відтворення:** `Measure-Command { docker build -t <image_name> . }` у репозиторії `lab-03-starter-project-python`.

| Тип образу / Зміни | Розмір | Час збірки | Особливості та причини |
| :--- | :--- | :--- | :--- |
| **Неоптимізований (Debian)** | ~150 MB | 2.82 с | Інструкція `COPY . .` стояла перед `RUN pip install`. Будь-яка зміна в коді збивала кеш, змушуючи Docker заново завантажувати всі залежності. |
| **Оптимізований (Debian)** | ~150 MB | 1.44 с | Спочатку копіювався `requirements/`, виконувався `pip install`, а потім копіювався код проєкту. Час збірки при зміні коду впав удвічі завдяки ефективному використанню кешу. |
| **Debian-slim + Numpy** | ~250 MB | 20.05 с | Швидке встановлення: пакетний менеджер завантажив прекомпільовані бінарники (wheels), спеціально зібрані для `glibc`. |
| **Alpine + Numpy** | ~100 MB | 32.24 с | Збірка тривала відчутно довше. Alpine використовує `musl libc`, тому встановлення потребує специфічних `musllinux` пакетів або компіляції C/C++ коду `numpy` прямо під час збірки образу. |

### 2. DNS-резолвінг: Musl (Alpine) vs glibc (Debian/Ubuntu)

**Мета:** Перевірити здатність різних базових образів резолвити неповне доменне ім'я (`myservice.internal`) з використанням пошукового суфікса (`--dns-search="corp"`).

**Відтворення:**
```bash
# Запуск кастомного DNS сервера:
docker run --rm -it --name dns-server --network dns-lab alpine sh -c "apk add dnsmasq && echo 'address=/myservice.internal.corp/10.0.0.50' > /etc/dnsmasq.conf && dnsmasq -k --log-queries --log-facility=-"

# Тестовий запит клієнта:
docker run --rm --network dns-lab --dns=<IP_DNS_SERVER> --dns-search="corp" <OS_IMAGE> getent hosts myservice.internal
```


### 3. Golang Application (Multi-stage builds)

**Мета:** Дослідити підхід багатоетапної збірки для статично компільованої мови Go для зменшення розміру та підвищення безпеки образу.
**Відтворення:** Репозиторій `deploy.lab-containers-starter-project-golang`, збірка командою `docker build`.

| Спосіб збірки | Розмір | Час збірки | Вміст та зручність |
| :--- | :--- | :--- | :--- |
| **Однокрокова (`golang:1.22`)** | 1.33 GB | 48.47 с | Включає вихідний код, компілятор Go та утиліти Debian. Зручно для розробки, але небезпечно для production через величезну площу атаки. |
| **Multi-stage (`scratch`)** | 16.7 MB | 8.57 с | Містить **лише** скомпільований бінарник. Абсолютно безпечно, але неможливо дебажити зсередини (відсутня оболонка `sh`). |
| **Multi-stage (`distroless`)** | 22.9 MB | 10.97 с | Бінарник + базові системні сертифікати (CA certs) та tzdata. Терміналу немає. |

## 📌 Загальні висновки та рекомендації

На основі проведених досліджень, сформовано наступні рекомендації стосовно упаковки застосунків у контейнери:

1. **Завжди використовуйте кешування шарів.** Інструкції у `Dockerfile` мають йти від тих, що змінюються найрідше (встановлення системних пакетів, копіювання файлів залежностей) до тих, що змінюються постійно (копіювання вихідного коду). Це кардинально прискорює CI/CD пайплайни.
2. **Будьте обережні з Alpine Linux.** Хоча він забезпечує мінімальний розмір базового образу, використання Alpine для застосунків на Python/Node.js/Ruby, які мають залежності на C/C++, може призвести до збільшення часу збірки (через компіляцію під `musl libc`) та проблем із DNS-резолвінгом у мікросервісних мережах. Для таких стеків рекомендується використовувати `debian-slim`.
3. **Застосовуйте Multi-stage builds для компільованих мов.** Для Golang, Rust чи C++ обов'язково розділяйте етап збірки (з важкими компіляторами) та етап виконання.
4. **Використовуйте `distroless` образи для production.** Використання `scratch` або `distroless` у якості фінального образу дозволяє зменшити розмір контейнера в десятки разів і позбавляє зловмисників доступу до командної оболонки (`sh`/`bash`), роблячи інфраструктуру значно безпечнішою.
